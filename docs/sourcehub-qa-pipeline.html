Capture QA Pipeline

A basic, on-device check that every photo a crowd worker takes shows the thing the task is about — a retail shelf, not the floor. It runs on the phone at the shutter, works offline, warns rather than refuses, and hands the reviewer a score. This is the record of what was built, how it decides, and where the knobs are.

Runs
On the phone, at the shutter
Model
Google ML Kit image labelling, on-device
Verdict
Warn + offer retake; a human rejects
Schema
No new tables, no migration
The governing rule

The score never deletes work by itself. On the phone it warns and offers a retake; in the console it orders the review queue. Only a person at gate 1 clicks reject.

A false refusal on a device is invisible and unpaid — the worker loses the shot and nobody learns of it. A false pass costs a reviewer a few seconds. The pipeline is built on that asymmetry, and it is why the device's verdict is recorded, shown and never trusted.

Part 1

The pipeline

One question per capture: does this image belong to the domain the task asked for? The answer is produced in four stages that already existed as places in the product; the pipeline joins them.

Four stages, one flow

Why this shape

The earlier three-tier design (ONNX on the server, a Celery worker, per-contract calibration) answers a harder question than the brief asks, and answers it after the upload — when the worker may already have left the site. The requirement here was basic, on the mobile, and about the domain of the image. Three facts in the codebase made the on-phone route cheap:

  • The phone already had a check socket: checkCapture() in mobile/src/validation/rules.ts produces findings that travel with the presign and land in asset.check_results.device[]. Nothing read them; now something does.
  • task.capture_spec is open JSON, inherited from the client's request and already sent to every assignment. The subject lives inside it; no column, no migration.
  • defect_code.wrong_subject was seeded from the start. The finding uses that code.

Google ML Kit's image labeller was chosen over CLIP-on-device because it is ~50 ms, needs no model download, works on the 2–3 GB Androids a crowd actually carries, and its ~400-label vocabulary separates shelf / dog / floor / selfie / screenshot — the cases a basic check exists to catch. The price is that the app must be a development build rather than Expo Go (see Part 8).

Part 2

The subject

A task without a subject gets no check. A task with one carries, in a few words, what a capture must and must not show.

What a task carries

task.capture_spec — the subject sits beside the existing keys
{
  "media": ["photo"],  "require_gps": true,  "orientation": "portrait",   // inherited from the request
  "subject": {
    "domain":        "retail shelf",                        // ≤ 80 chars; the dialog's headline
    "must_show":     ["shelf", "products", "price tags"],   // ≤ 12 phrases of ≤ 60 chars
    "must_not_show": ["person", "selfie", "screenshot"],
    "labels":        []                                     // optional: an explicit ML Kit vocabulary
  }
}

Short phrases, not sentences. The phone compares the words of domain and must_show with the labels the model produces, so "price tags" is useful and "make sure the price tags are readable" is noise. labels exists for the case where the aggregator knows exactly which ML Kit labels to expect; when set it replaces the other two lists for scoring and is left empty by default. Validation is SubjectIn in backend/src/sourcehub/api/v1/delivery.py.

Where it is typed

In the console's Assign a task dialog (frontend/src/features/delivery/pages.tsx, AssignTaskDialog), three new fields: Subject, Must show, Must not show. They are prefilled from the client's request brief the dialog already loads — subject type and location type from the sampling frame, and a fixed default of person, selfie, screenshot — by a deterministic function (draftSubject). No language model is involved; the prefill saves typing and the partner's own words are what get saved. Leaving the Subject field empty assigns a task with no check.

The task detail dialog shows the saved subject as one row, so what the worker will be held to is visible to whoever opens the task.

How it reaches the phone

The console sends the subject as its own field (subject) rather than inside capture_spec. That matters: a capture_spec in the create-task body replaces the one inherited from the request, which would silently drop the client's media, GPS and tilt answers. create_task (modules/delivery/service.py) inherits first and then merges: capture_spec = {**inherited, "subject": subject}.

From there nothing new happens. _assignment_dict already sends the whole spec to the worker, and the phone's CaptureSpec type gained an optional subject. On the assignment screen it is rendered as its own What to capture card above the technical requirements — the one line to read before the first shot — and excluded from the generic key list that card used to print.

Part 3

On the phone

Everything below is in mobile/src/validation/subject.ts (pure, unit-tested) and mobile/src/capture/useCapture.ts (the wiring). Photos only; a video's frames are left to a later server-side stage.

At the shutter

  1. The camera returns the file, its pixel size and EXIF. It is moved into the app's private directory and the GPS fix resolved, as before.
  2. checkCapture() runs the existing rules — media kind, size cap, megapixels, orientation, tilt, GPS. A block here still deletes the file and refuses it; the subject check never runs on a capture that failed a stated condition.
  3. If the task has a subject and the capture is a photo, labelImage(uri) asks ML Kit what it sees: a list of {text, confidence} such as Shelf 0.91, Supermarket 0.80, Floor 0.30. Two-second timeout; any failure yields null and the check is skipped.
  4. scoreSubject(labels, subject) produces the score; subjectFinding() turns a low one into a finding.
  5. No finding → the capture is queued and the uploader kicked, exactly as before. A finding → the file stays on disk, unqueued, and the capture screen asks the worker.

The score

scoreSubject — label overlap
wanted    = words(subject.labels)  if set, else  words(domain) ∪ words(must_show)
forbidden = words(must_not_show)

hit   = labels whose text shares a word with wanted,    best confidence first
veto  = labels whose text shares a word with forbidden

score = clamp( best(hit).confidence − best(veto).confidence , 0, 1 )
seen  = the five most confident labels, for the reviewer

words() lowercases, splits on non-letters, drops filler (a, the, of, with…) and words under three letters, and stems just enough for a plural to meet its singular: shelves → shelf, products → product, groceries → grocery. Nothing more clever than that, on purpose: the reviewer can read the labels and reproduce the number in their head.

What the score can and cannot say: it separates shelf from not-shelf. It cannot separate "a shelf with price tags" from "a shelf" — ML Kit's vocabulary has no price tag. That is the known ceiling of a label check, and the reason the reviewer sees the labels rather than only the number.

Keep or retake

Below the cut, useCapture returns an outcome instead of queueing:

mobile/src/capture/useCapture.ts
type CaptureOutcome =
  | { kept: true;  findings: Finding[] }
  | { kept: false; finding: Finding; keep(): Promise<Finding[]>; retake(): Promise<void> };

The capture screen shows a native alert titled Doesn't look like retail shelf with the message Saw: floor, flooring, tile. Keep it anyway, or shoot it again?

  • Keep → keep(): the outbox row is inserted with the warning in its checks, the uploader is kicked, the counter advances. Same path as any other kept capture.
  • Retake → retake(): recordRejections() writes a local refusal with code wrong_subject and the file is deleted — the same pair the existing block path uses, so the assignment screen's "refused on this phone" count and its label (retaken: didn't show the subject) work without further code.

Neither answer reaches the server as a decision. A retaken file never existed as far as the API knows; a kept one arrives as an ordinary asset with a note attached.

When there is no labeller

ML Kit is native code, absent from Expo Go and from any build made before this change. labelImage() requires the module lazily inside a try; if it is missing, or the call throws, or six seconds pass, it answers with the reason (no_labeller, error, timeout) and the capture is queued with a warning of its own, subject_unscored. The worker is not asked anything — they did nothing wrong — but the tile at gate 1 reads unchecked and the queue column says n not checked on phone. The pipeline degrades to "the worker read the card", and it says so, because a skipped check that looks exactly like a passed one once cost a day of "is it even running?" on the first preview APK.

A pass is visible too: after a photo that scores at or above the cut, the viewfinder shows a green Looks like retail shelf. for the next shot.

For trying the dialog without a build, EXPO_PUBLIC_SUBJECT_STUB=Floor:0.9,Hand:0.6 in mobile/.env makes every photo "see" those labels. It must be absent in any build that leaves the developer's machine.

Part 4

With the upload

The channel existed; it grew two optional fields.

The presign request (POST /assignments/{id}/assets/presign) carries the phone's findings as checks[]. DeviceCheck in api/v1/media.py now accepts score (0–1) and detail (≤ 1 KB of JSON) alongside code, severity and message; older builds that send neither are unaffected. presign_asset stores the list verbatim as asset.check_results = {"device": [...]}, as it always did.

asset.check_results.device[0] — a kept floor shot
{
  "code": "wrong_subject",
  "severity": "warn",
  "message": "Doesn't look like retail shelf. Saw: floor, flooring, tile.",
  "score": 0,
  "detail": { "labels": ["Floor", "Flooring", "Tile"], "hit": [], "veto": [] }
}

The server does nothing with it. It does not change the asset's status, does not gate confirm_asset, does not enter any decision. It is recorded, and read by the console.

Part 5

At gate 1

The aggregator's own review of a worker's batch. The pipeline changes what they see first, not what they can do.

  • Queue order. gate1_queue() (modules/qa/service.py) counts, per submitted batch, the ready assets whose check_results->'device' contains a wrong_subject entry (a jsonb containment test, @> '[{"code":"wrong_subject"}]'). Batches with any come first; within each group, oldest first as before. The row carries the count as off_subject.
  • Queue table. A Phone check column: an amber N may be off-subject pill, or a dash.
  • Gallery. Assets now return device_checks; a tile whose checks include wrong_subject wears a small subject? badge. The preview's detail list ends with Phone check: Doesn't look like retail shelf. Saw: floor… · score 0.00.
  • Decision. Accept and reject are the existing buttons with the existing rules. The badge is a place to look, not a recommendation.
Part 6

Knobs and calibration

Three constants in mobile/src/config.ts and subject.ts, and a procedure for setting the one that matters.

ConstantDefaultMeaning
SUBJECT_OFF0.30Below this the worker is asked. A starting guess, to be replaced by a measured value.
SUBJECT_DIALOGtruefalse is shadow mode: score and attach the finding, never show the dialog. The reviewer still sees everything.
LABEL_TIMEOUT_MS6000Longer than this and the photo is queued with subject_unscored (timeout). ML Kit's first call loads the model and decodes the full-size JPEG; on a mid-range phone that passed the original two seconds, which is why it is six.
Setting the cut from data

Ship the first crowd build in shadow mode. Every gate-1 accept/reject is then a label against a score. After a couple of weeks or a few hundred assets, read check_results against the verdicts: choose the cut as the loosest value at which the reviewer rejected no more than about 5% of what the phone would have passed, and confirm that most of what it would have flagged was indeed rejected. Then set SUBJECT_OFF, flip SUBJECT_DIALOG, and rebuild.

The same data answers whether the label check is worth its keep at all, which is the question that decides on the server-side upgrade in Part 7.

Part 7

What it does not do

  • Fine distinctions. "Shelf" is as specific as ML Kit gets; with price tags, fully stocked, this brand are out of reach.
  • Video. Photos only. A first-frame check is possible later; a server can sample frames.
  • Web uploads. Captures uploaded through the console's own upload dialog carry no labels and are never flagged.
  • Trust. The device can be lied to. That is fine because it decides nothing; it is why a server-side score would be the authoritative one if one is ever needed.
  • Learning. Nothing adapts. The cut is a constant, set by hand from the data above.
The upgrade path, if the data asks for it

A server-side scorer (MobileCLIP-S0 on CPU, ~20 MB, via ONNX Runtime) that embeds each uploaded image and scores it against the same subject phrases plus a bank of distractor prompts, and against the client's own capture_examples. It would cover video and web uploads, understand "price tags", and write its verdict beside the phone's — never averaged with it. It needs one worker process and a small table; the design exists in the session notes and is not started.

Part 8

Building and testing

The one structural cost of the pipeline is that the app is no longer runnable in Expo Go.

The development build

ML Kit is native code, so the app is compiled with it via EAS. mobile/eas.json defines development (dev client, internal APK), preview (plain APK for the crowd) and production; expo-dev-client is a dependency; app.json carries the EAS project id under the jituexpo2026s-team organisation. The first development build was made on 18 September 2026 (eas build -p android --profile development). A development build loads JavaScript from Metro exactly as Expo Go did, so day-to-day work is unchanged: npx expo start --dev-client, open the app, edit, reload. A rebuild is needed only when native dependencies change.

On the device

The full manual run is Part 9. The first device run, on 18 September 2026, confirmed ML Kit executing on the phone and the dialog appearing.

Found in testing: portrait photos refused as landscape

On the development build every upright photo on a portrait task was blocked by the pre-existing orientation rule. Android stores the frame in the sensor's landscape orientation and records the quarter turn in the EXIF Orientation tag (6 or 8), so a portrait shot reports 4000×3000. displayedSize() in rules.ts now swaps the dimensions for tags 5–8; the capture screen forwards photo.exif.Orientation. Unit-tested; verified on the phone.

Part 9

Testing the flow

One run through all four stages, by hand, with the real model. It takes about twenty minutes once the build is on the phone, and it proves every claim in Parts 2–5 with something you can see.

Before you start

Servers

API and console running

  • cd backend && .venv/Scripts/python -m uvicorn sourcehub.main:app --host 0.0.0.0 --port 8000 --app-dir src
  • cd frontend && npm run dev → http://localhost:5173
  • http://localhost:8000/health answers; port 8000 open on the private firewall profile
Phone

Development build installed

  • Android phone on the same Wi-Fi as the PC
  • The APK from eas build -p android --profile development installed (allow "install unknown apps")
  • mobile/.env has no EXPO_PUBLIC_SUBJECT_STUB line
  • cd mobile && npx expo start --dev-client; open Cosarathi Capture (not Expo Go), pick the Metro server
Accounts

Three sign-ins

  • Partner: partner@northstar.example
  • Aggregator: crowd@bengaluru.example
  • A crowd worker under AG-01 with a known password, signed in on the phone with the API URL http://<pc-wifi-ip>:8000

Seeded passwords are in the repository README and are for local development only.

A · The task carries a subject

  1. In the console as the partner, open the active contract → Assign a task. Note the callout Inherited from the request (photo only, GPS required): that is what the subject must not overwrite.
  2. Fill in — title Subject check trial, target 6 photos, and the three new fields: Subject retail shelf, Must show shelf, products, price tags, Must not show person, selfie, screenshot. Assign to Bengaluru Crowd.
  3. Open the new task in the list. Check the detail dialog has a Subject row: retail shelf · must show shelf, products, price tags · not person, selfie, screenshot.
  4. Sign in as the aggregator, open the task, assign 6 photos to the test worker.

B · The phone scores, the worker decides

  1. On the phone, open the assignment. Check a What to capture card sits above Capture requirements, and the requirements still list media: photo and require gps: true — the merge kept the client's spec.
  2. Tap Start and capture and take the six shots below, waiting for the counter or the dialog after each. Hold the phone upright throughout (the request asks for portrait).
#ShootExpectDo
1A real shelf with productsNo dialog; green Looks like retail shelf.; 1 saved—
2The floorDialog Doesn't look like retail shelf. Saw: floor, … — note the labels and the delay after the shutterRetake → counter stays at 1
3The floor againSame dialogKeep → 2 saved
4Your own faceDialog — person is forbidden, even with a shelf behind youRetake

  1. Tap Done. Check the assignment screen shows 2 × retaken: didn't show the subject under refused captures, and four captures in the gallery going uploading → ready.
  2. Submit for review.
If shot 1 shows no green line and shot 2 raises no dialog

The labeller could not answer, so the capture was queued with subject_unscored — the designed fallback, and it names its reason. Read it at gate 1: open the batch, click the unchecked tile, and the Phone check row says this build has no image labeller (Expo Go, or an APK built without the module), the check took too long (a slow first run — shoot again; the model is warm now) or the image labeller failed with the native message. On a development build the same reason is in the Metro terminal.

C · The reviewer sees it

  1. In the console as the aggregator, open Review (gate 1). Check the worker's batch is at the top and its Phone check column reads 1 may be off-subject (2 if shot 5 was flagged and kept).
  2. Click Review. In the gallery, check the kept floor shot wears the subject? badge and the shelf shots do not.
  3. Click the badged tile. Check the preview's last row: Phone check: Doesn't look like retail shelf. Saw: … · score 0.00. Those labels are ML Kit's actual output for that photo.
  4. Decide either way. Reject with a note and the worker's phone shows the rejection and can capture again; Accept and the batch proceeds. In both cases the flag decided nothing.

D · Controls

  • No subject. As the partner, assign a second task with the Subject field cleared. On the phone it has no What to capture card and the floor shot raises no dialog; at gate 1 its Phone-check column shows a dash.
  • Orientation. On the portrait task, turn the phone sideways for one shot: it is blocked with the landscape message, upright shots are not (the EXIF fix in Part 8).
  • Shadow mode. Set SUBJECT_DIALOG = false in mobile/src/config.ts, reload, shoot the floor: no dialog, but the capture still arrives at gate 1 flagged with its score.

What to write down from the run: the labels and score for each flagged shot (from the gate-1 preview), the shutter-to-dialog delay on that phone, and whether 0.30 felt right. Those are the inputs to Part 6.

Without a build

Everything except the model itself can be exercised in Expo Go. Put EXPO_PUBLIC_SUBJECT_STUB=Floor:0.9,Hand:0.6 in mobile/.env, restart Metro, and every photo "sees" those labels — so every shot raises the dialog and steps B3 onward, C and D behave exactly as above. Change the value to Shelf:0.9,Supermarket:0.8 to see the silent path. Remove the line before any build.

The automated suites (npm test in mobile/, pytest tests in backend/, npx tsc --noEmit in both front ends) cover the scoring arithmetic, the validation limits and the merge; they run in under a minute and need no phone.
