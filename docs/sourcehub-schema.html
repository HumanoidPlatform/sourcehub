Part one

Where things live

Three stores, a strict division of labour, and one connection rule that decides whether any of the isolation below actually works.

Postgres 16 · docker volume

Every fact

Organisations, users, hashed credentials, role grants, the RFP→proposal→contract→task chain, equipment custody, double-entry money, the audit chain. One database, one shared schema, row-level security as the tenancy boundary.

Never holds: file bytes
MinIO · 3 buckets

Bytes, eventually

sourcehub-assets, -documents, -bundles. When the media plane lands (milestone 3), captured files go straight here via pre-signed URLs; the database keeps only storage_key, sha256 and the manifest. Bytes never traverse the API.

Never holds: anything queryable
Redis

Work in motion

Celery queues (media · qa · notify) and cache. Rebuildable from Postgres at any moment.

Never holds: anything that must survive a restart
The connection rule

The application connects as sourcehub_app — a role that is neither the table owner nor holds BYPASSRLS. Migrations and isolation tests use the owner.

A superuser bypasses row-level security unconditionally, so an API using the postgres account has all 89 policies enabled and entirely ineffective — the most common way this control fails silently. This is also why proving isolation by querying as postgres proves nothing.

Part two

The six rules every table obeys

Stated once here; assumed everywhere below.

R1

UUID keys, human codes

Primary keys are uuid (gen_random_uuid()). Beside each sits a reference_code from a real sequence — CL-01, RFP-1002, CTR-01. People and support tickets say codes; machines join UUIDs.

R2

One status enum per entity

The prototype shared 28 status strings across every table — ambiguous, because submitted on a proposal awaits the client while on a task it awaits the partner's QA. Here each entity has its own Postgres enum; an illegal value cannot be written at all.

R3

Soft delete; three tables append-only

Deletion is deleted_at, never a lost row. qa_review, ledger_entry and audit_event go further: rewrite rules forbid UPDATE and DELETE outright. A correction is a new row.

R4

Audit columns everywhere

created_at, updated_at (trigger-maintained), created_by, updated_by on every mutable table.

R5

Derived beats duplicated

The request row stores only what its owner can write (draft · published · accepted · cancelled). Everything after award — in progress, delivered, completed — is derived from the contract, so two state machines can never drift apart.

R6

jsonb only for genuinely open shapes

onboarding_request.payload, contract.rubric_snapshot, notification.link_params, future asset.metadata. Anything filtered, sorted or joined on gets a real column — which is why each org kind has a typed profile table instead of a blob.

Part five

How a login becomes a permission set

“Logins controlled from the database table” is four tables and three functions — no role name is ever checked in code.

the resolution chain — every step is a table lookup
-- 1 · who are you?           (SECURITY DEFINER: no org context exists yet)
SELECT * FROM authenticate_lookup('partner@northstar.example');
   → app_user: password_hash (argon2id), status, locked_until

-- 2 · who may you be?
SELECT * FROM user_organisations(:user_id);
   → user_role_grant ⋈ organisation ⋈ role — one row per live grant;
     one org auto-selects, several make the console ask

-- 3 · what may you do there?
SELECT code, requires_mfa FROM user_capabilities(:user_id, :org_id);
   → grant ⋈ role_permission ⋈ permission — the capability set the JWT carries,
     re-resolved on every refresh so a revoked grant dies within one token TTL

The token then carries {user_id, org_id, org_kind, role, caps[]}; the API checks can('proposal.accept') and Postgres checks the rows. Moving one user_role_grant row makes the same email log in as something else — no deploy.

Decision

Credentials live in Postgres now; Keycloak is a seam, not a dependency.

app_user.external_idp / external_idp_subject sit dormant. Adopting an IdP later means populating them and swapping one adapter — roles, grants and capabilities stay exactly where they are, in these tables.

Part six

Tenancy — two axes, enforced in the database

Conflating these two is the most likely data-leak bug in this product, which is why neither lives in application WHERE clauses.

Account axis

org_id = current_org_id()

One client from another, one tenant from another. Every request opens a transaction and pins app.org_id, app.role, app.user_id with SET LOCAL; with no context set, current_setting(…, true) returns NULL and every policy fails closed to zero rows.

Network axis

parent_org_id = current_org_id()

A supplier belongs to exactly one tenant and is invisible to every rival — including one bidding on the same request. Siblings under the same tenant do see each other (an aggregator borrows from its network's sponsors); a rival network has a different parent.

TN-01 NorthStar ── AG-01 · AG-02 · BZ-01 · BZ-02 · DS-01 · DS-02
TN-02 Meridian  ── AG-03 · BZ-03 · DS-03  ⟂ no path across

A client reaches a supplier only by traversing a contract it owns — which is what makes supplier attribution safe to show on the delivery breakdown. Verified live: TN-01 sees 7 organisations (itself + its 6), TN-02 sees 4, and with no context every table returns nothing.

The 20 sanctioned holes

SECURITY DEFINER functions are the only code that sees past RLS, each one narrow and named: the pre-context steps (authenticate_lookup, session_lookup, invitation_accept, password reset), the helpers policies need to avoid recursing into themselves (current_org_parent_id, org_visible_via_contract, …), the audit chain head, and the platform's own id. Everything else queries as you.

Field notes — what testing the policies actually caught

All eight live in db/110_auth_functions.sql with their reasoning; they are the difference between RLS that works and RLS that decorates.

  1. Policies default to FOR ALL, and permissive policies OR together. A read predicate silently became a write grant — a tenant could insert its own approval. Every read policy is now explicitly FOR SELECT; writes have their own, narrower policies. 42 policies became 89.
  2. INSERT … RETURNING must also pass the SELECT policy. A notification addressed to another org failed at commit — after the 2xx had gone out. Cross-org inserts avoid RETURNING; the API commits before responding.
  3. An audit chain read under RLS forks per org. Each org chained onto its own last visible event — no single tamper-evident chain. The append is DEFINER; the actor recorded is still the caller.
  4. A deferred trigger runs under whatever context commits. The ledger balance check saw only the client-side leg of a balanced transaction and refused it. An integrity invariant is about all rows by definition — DEFINER.
  5. Bidders must be visible to the client they bid to — before any contract exists, or the comparison table joins to org rows the client cannot see and shows nothing.
  6. Bidding on a request is a durable reason to see it, or a losing bidder's own proposal history goes dark the moment the award lands.
  7. Network siblings see each other. An aggregator must browse its own network's sponsor inventory before any loan exists.
  8. The reviewer moves the thing it reviews. Gate 2 closes a submission, and the reviewer is the partner, not the supplier — without its own UPDATE policy the verdict updated zero rows, silently.
Part seven

How money moves

Two moments touch money, both written under a transaction-local platform elevation inside the caller's own transaction — atomic with the business change, and only because RLS says organisations never write ledger rows themselves.

MomentLedger effect (every transaction balances)Invoice effect
Award
client accepts a proposal		 debit client.receivable · credit platform.escrow — the 50% milestone held “Milestone 1 of 2” pending
Approval
client accepts the delivery		 remainder joins escrow → client payment settles the receivable into cash → escrow empties: partner.payable gets value − fee, fee_income gets the fee all contract invoices paid · “Platform fee, 9%” raised against the partner, paid
After completion, live: receivable 0 · escrow 0 · cash +value · payable value−fee · fee_income +fee · ledger_imbalance = 0 rows.
Part eight

Append-only structures and scale

Three tables where history is the product, and the physical design for the two that grow without bound.

TableMechanismWhy
audit_event rewrite rules block UPDATE/DELETE · row_hash chains over the previous row · range-partitioned by quarter · GIN on scope[] · BRIN on time tampering must be detectable, not merely discouraged; panels filter by “events touching this entity” at any size
ledger_entry rewrite rules · deferred balance trigger · corrections are reversing transactions money history is evidence; an edited ledger is not a ledger
qa_review rewrite rules · one row per gate per attempt which gate caught a defect decides who absorbs the rework — collapsing verdicts into one flag loses who owes what
asset range-partitioned by month (PRIMARY KEY (id, created_at)) · BRIN on time · bytes in MinIO, manifest here the year-one target is 40 million rows and 80 TB/month of ingest; old ranges detach for archive without touching the live set

Source of truth: db/000–110 apply in filename order on a fresh volume (56 tables, 89 policies); db/900_seed.sql is the minimum a deployment needs — 38 permissions, 6 roles, the platform org, one admin; db/910_seed_demo.sql is the prototype's world and is deleted before any real deployment. Where this document and the running schema disagree, the schema is right and this document needs a revision — the same contract the blueprint makes with the prototype.
