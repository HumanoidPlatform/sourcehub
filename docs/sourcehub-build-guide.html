The governing constraint

Everything runs on a developer laptop now; everything moves to Azure later. That single sentence should decide every technology argument on this project, because the expensive failure mode is not picking a mediocre library — it is picking something with no local equivalent, or something that only exists locally and has to be torn out at migration time.

The rule

Every component must have both a container you can run locally and a managed Azure service that speaks the same protocol. Where no such pair exists, the difference is hidden behind an adapter in platform/ and nowhere else.

There are exactly five places where local and Azure genuinely differ — object storage, identity, secrets, email and telemetry. Five adapters, roughly 200 lines each, is the entire cost of the migration. Everything else — Postgres, Redis, FFmpeg, ClamAV — is byte-identical because it is the same software running in the same container image on both sides.

What this rules out

No Azure-only building blocks in the core: not Durable Functions, not Logic Apps, not Cosmos DB, not Azure Media Services — which was retired in June 2024 and should not appear in any design put in front of an architecture board.

Adopting them would mean the local stack diverges from production on day one, so nobody can run the real system on a laptop and every bug becomes an "it works locally" argument. The cost of the rule is giving up some managed convenience; the benefit is that the thing you develop against is the thing you ship.

The stack

Data layer and row-level security

The blueprint makes RLS the tenancy boundary. Three implementation details decide whether that works or quietly does nothing.

  1. The application must connect as a role that is neither the table owner nor holds BYPASSRLS. Table owners bypass their own policies by default, so an app connecting as the owner has RLS enabled and entirely ineffective — the most common way this control fails silently.
  2. SET LOCAL only lasts for a transaction, so every session must open one before setting the org context. A session that queries outside a transaction gets no context and, correctly, sees nothing.
  3. Use current_setting('app.org_id', true) with the missing-ok flag, so an unset context returns NULL and the policy fails closed rather than raising.
src/sourcehub/db/session.py
from contextlib import asynccontextmanager
from sqlalchemy import text
from sqlalchemy.ext.asyncio import async_sessionmaker

SessionLocal = async_sessionmaker(engine, expire_on_commit=False)

@asynccontextmanager
async def org_session(org_id: str, role: str):
    """Every query in the app runs inside one of these. There is no other way
    to get a session, which is what makes forgetting the context impossible."""
    async with SessionLocal() as session:
        async with session.begin():          # SET LOCAL needs a transaction
            await session.execute(
                text("SELECT set_config('app.org_id', :org, true), "
                     "       set_config('app.role',   :role, true)"),
                {"org": org_id, "role": role},
            )
            yield session
migrations/versions/0003_rls_contract.py — policies are hand-written, never autogenerated
op.execute("ALTER TABLE contract ENABLE ROW LEVEL SECURITY")
op.execute("ALTER TABLE contract FORCE ROW LEVEL SECURITY")   # applies to the owner too

op.execute("""
CREATE POLICY contract_visibility ON contract
  USING (
    client_org_id  = current_setting('app.org_id', true)::uuid   -- the buying client
    OR partner_org_id = current_setting('app.org_id', true)::uuid -- the delivering partner
    OR EXISTS (                                                  -- a supplier on one of its tasks
      SELECT 1 FROM task t
      WHERE t.contract_id = contract.id
        AND t.assignee_org_id = current_setting('app.org_id', true)::uuid
    )
  )
""")
Decision

Ship the three-context isolation test with the very first table, not once the schema settles.

A parametrised pytest fixture runs every list endpoint as the owner org, a sibling org of the same kind, and an unrelated org, and fails if a sibling or unrelated context sees a single row. Written once, it covers every endpoint added afterwards automatically. Retrofitting it after fifty endpoints exist means triaging fifty failures at the worst possible moment.

Background work

Three Celery queues with different characteristics, deliberately not one:

QueueWorkConcurrencyTimeout
mediaChecksum, scan, probe, transcode, thumbnail, automated checksCPU-bound, prefork, 1 per core30 min soft, 45 hard
qaSampling draws, gold-set comparison, rubric evaluation, bundle assemblyMixed, 4 per worker5 min
notifyEmail, webhook delivery with backoff, digest assemblyIO-bound, gevent, 50 per worker30 s
 Separating them means a backlog of 900 hours of video transcoding cannot delay a password-reset email, and each queue scales on its own KEDA rule once this reaches Azure Container Apps.

Every task is idempotent and keyed on a domain id, with acks_late=True and reject_on_worker_lost=True, so a worker killed mid-job causes a redelivery rather than a lost asset. Tasks take ids, never objects — a task argument that contains a serialised row is a task that operates on stale data the moment the queue backs up.

Front end

Decision

A React and TypeScript single-page app for the console, despite the backend being Python end to end.

The console is genuinely application-shaped rather than document-shaped: a command palette, role switching, dialogs with focus management, live-updating tables, optimistic QA decisions. HTMX with Jinja templates is a real option and would keep the project single-language — if the team would rather trade some interaction polish for that, it is a defensible call and the design tokens work either way. What is not defensible is starting with server templates and bolting a SPA on later, so decide this now.

The reference build's CSS token layer transfers unchanged — it is plain custom properties with no framework assumptions. Port it to a single tokens.css, build the components as React components over the same class names, and keep the design-system page as a route so it stays generated from live code.

Part three

Local to Azure

The migration is not a project. It is five adapter implementations, a Bicep template and a connection-string change — provided nothing outside platform/ ever imports a vendor SDK.

The five seams

The storage adapter, in full

This is the one seam worth showing completely, because it is the one that carries the product's hardest requirement and the one where S3 and Azure Blob genuinely differ. S3 has multipart upload with UploadId and part numbers; Blob has Put Block and Put Block List with base64 block ids. Both can be signed for direct browser upload, so the protocol below fits both — but only if it is defined in those terms from the start.

src/sourcehub/platform/storage/base.py
class ObjectStore(Protocol):
    async def begin_upload(self, key: str, parts: int, content_type: str) -> UploadTicket:
        """Return one signed URL per part plus whatever the backend needs to
        finalise: an S3 UploadId, or the block-id list for Azure Blob."""

    async def finish_upload(self, ticket: UploadTicket, etags: list[str]) -> ObjectStat: ...
    async def abort_upload(self, ticket: UploadTicket) -> None: ...
    async def signed_download(self, key: str, ttl: int = 900) -> str: ...
    async def open_stream(self, key: str) -> AsyncIterator[bytes]: ...   # workers only
    async def stat(self, key: str) -> ObjectStat: ...
    async def delete(self, key: str) -> None: ...
Azure note

Do not reach for a generic filesystem abstraction such as fsspec or smart_open for this.

They abstract reading and writing well and pre-signed URLs not at all — and pre-signed URLs are the entire point of the upload design. A hand-written adapter of roughly 200 lines per backend gives full control over TTLs, content-type pinning and part sizing, all of which you will need to tune. Use those libraries for incidental file work if you like; keep them out of the ingest path.

The rule that keeps this navigable: every module has the same six files. An engineer who has read identity/ can find their way around ledger/ without asking. Resist the urge to let a large module grow its own private structure — split it into two modules instead.

Running it locally

Makefile — the entire developer interface
make up        # build images, start all ten services, wait for health
make seed      # migrate, then load the demo orgs, requests and contracts
make test      # pytest with a throwaway Postgres via testcontainers
make lint      # ruff + mypy + import-linter
make revision  # alembic autogenerate, then remind you to hand-write the policies
make logs s=api
make down

The seed data is the same fixture set the reference build ships with — three clients, three delivery partners, their networks, and requests at every lifecycle stage. Nobody should ever have to click through the UI to create test data, and a demo should never begin from an empty database.

Decision

No mocks for infrastructure in tests. Tests run against real Postgres, real Redis and real MinIO in throwaway containers.

Mocked storage cannot tell you that your pre-signed URL has the wrong content-type pinned, and mocked Postgres cannot tell you that your RLS policy has a hole. Those are precisely the two failures that would reach production. Testcontainers makes the honest version fast enough — roughly forty seconds for the full suite — that nobody is tempted by the dishonest one.

Part five

Build order

Sequenced so that the riskiest and most structural work happens while changing it is still cheap. The first two milestones deliberately produce very little visible product — and skipping them is the most expensive decision available on this project.

Milestone 0

Walking skeleton

Weeks 1–2
  • Compose stack, all ten services healthy
  • make up and make seed work
  • One table, one endpoint, RLS on, three-context test passing
  • CI running every stage
  • Storage adapter with both implementations and its contract test
Milestone 1

Identity and tenancy

Weeks 3–5
  • Keycloak realms, org and user model, role grants
  • Auth dependency producing the org session
  • Capability matrix in policies.py
  • Audit module, since everything below writes to it
  • Console shell: rail, top bar, role switching, design system route
Milestone 2

The transaction

Weeks 6–11
  • Requests, proposals, award, contracts, tasks
  • Network module: partners, equipment, loans
  • Manual QA at both gates, no automation yet
  • Notifications in-app and by email
  • A real client and partner can close a loop
Milestone 3

The media plane

Weeks 12–20
  • Upload orchestration, the full sequence in figure 2
  • Worker pool, all three queues
  • Automated checks and the rubric compiler
  • Sampling plans and gold sets
  • Capture app, if a partner is ready to pilot
Milestone 4

Money

Weeks 21–26
  • Ledger module, double-entry, reconciliation job
  • Payment provider integration, escrow, payouts
  • KYB, tax collection, DAC7 groundwork
  • Dispute workflow and the ops console
Milestone 5

Azure

Weeks 27–30
  • Bicep for Container Apps, Postgres, Redis, Blob, Key Vault
  • Entra External ID replaces Keycloak
  • Blob adapter promoted from tested to live
  • Azure Monitor exporter, alerting, error budgets
  • Restore drill before any real client data lands
The sequencing risk

Milestone 0 produces nothing demonstrable, and there will be pressure to skip to milestone 2.

Every item in it is structural: RLS, the storage seam, the isolation test, CI. Each one is a day's work now and a rewrite later, because they are the assumptions every subsequent line of code is written against. Protect that fortnight. If it must be cut, cut the capture app from milestone 3 instead — that one can genuinely be deferred without touching anything already built.
